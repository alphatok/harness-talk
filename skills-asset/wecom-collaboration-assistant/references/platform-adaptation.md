# 跨平台自适应初始化

目标是让本次任务能运行。由助手诊断、查询资料、选择方案、执行修复并复验。检测脚本保持只读；安装、升级与授权由助手在用户已要求的初始化范围内编排。无需让普通使用者编写命令。

## AI助手与宿主适配

先识别宿主，再识别操作系统。适配依据是当前实际能力，不按客户端名称假定全部功能可用。

| 宿主条件 | 运行方式 |
| --- | --- |
| 原生支持Skill目录 | 按当前宿主的官方安装路径与格式加载完整包，保留相对引用 |
| 可读取文件或项目规则，无原生Skill机制 | 读取SKILL.md与当前任务相关参考；需要规则文件时新增适配入口，不覆盖原规则 |
| 有文件与命令执行能力 | 用实际解释器运行脚本；企微CLI在该执行环境完成安装与授权 |
| 有企微连接器，无本机命令执行能力 | 使用当前连接器完成其支持的操作；本地脚本改由可用工具处理或人工协助 |
| 只能对话或接收附件 | 整理材料、生成计划与操作指引；无法执行的在线写入和桌面动作明确保留待办 |

遇到未适配宿主，先查其当前help、已有配置和官方资料，尝试可用的Skill、规则、文件加载或连接器方式；在本次任务目录保留适配入口即可。不能把所有客户端都安装到`.codex`，也不能默认`$skill-name`语法通用。不同宿主的权限、登录、后台服务与聊天绑定分别验证；换宿主后不能复用未经核实的会话标识。

手机消息接入需桥接器具有当前宿主的消息投递与回复适配。优先宿主已有官方集成或当前已具备组件；核对接收、投递、执行与回复。`wecom-codex-bridge`仅作为Codex专用的可选组件，不作为其他助手的默认依赖。其他宿主缺桥接时先研究并尝试适配，未完成前保留文档链接协作和手动提交请求的可用方式，不将其报告为远程聊天已接通。

## 识别现状

先用当前工具识别系统、CPU架构、Shell、可写目录、网络和权限。区分 Windows 原生、WSL、容器与远程终端；解释器、CLI、授权和文件路径尽量留在同一环境。不能直接把 macOS 路径或 WSL 路径交给 Windows 进程。

优先已有连接器。只整理材料时不安装 Node 或企微 CLI；已有连接器足够时不强制安装 CLI。桌面自动化缺失时仍继续本地整理和可用的接口操作，明确剩余人工步骤。

| 环境 | Python发现顺序 | 缺依赖时的候选路径 |
| --- | --- | --- |
| macOS | python3、python，再核对版本和架构 | 已有 brew；或 Python、Node 官方安装包/适配架构的发行包 |
| Windows | py -3、python、python3，逐个实际检查 | 已有 winget；或 Python Install Manager、Node 官方安装包 |
| Linux / WSL | python3、python | 现有发行版包管理器；无管理员权限时查询官方用户目录安装方案 |
| 其他系统或受限设备 | 当前工具能否启动兼容Python、连接器或CLI | 查官方支持矩阵及实际错误；可用运行时、已授权远程环境或人工执行 |

候选不是保证存在的命令。先检查命令和当前 help。Windows 的 python 可能只是商店别名，必须执行版本探测，不能只看 PATH。选择 Python 3.10+ 后记录真实解释器路径；后续执行使用该路径或已验证的启动器。脚本路径从本包位置解析，工作目录不限于 Skill 根目录。

Python可用后运行 `scripts/check_environment.py`；确需企微再加 `--wecom`。输出包含系统、架构、可见包管理器及CLI状态。脚本不能检查缺失的Python，因此Python发现由助手先执行。Python低版本、缺包、授权未完成和在线文档未验证分别报告。

## 按当前证据修复

1. 查询已安装工具的 `--help`、`--version` 和本次错误。缺安装工具时查询供应方官方安装文档。资料中的命令先核对当前系统与架构，不能直接运行网页中的任意脚本。
2. 选择最小修复。优先已有运行时、当前用户目录或当前任务目录；安装前说明安装对象与位置。既有授权涵盖的常规安装直接执行。系统提权、企业策略限制或需本人扫码时，说明具体需求，由使用者完成必要步骤。不要用管理员权限掩盖普通目录权限问题。
3. 安装或升级后，重新发现可执行文件并实际运行版本检查。新进程可能未继承新PATH，先用真实绝对路径继续；不反复安装。新会话需求单独说明，不擅自覆盖Shell配置。
4. 再执行最小功能检查。失败时根据新错误调整方案；同一错误没有新证据就不重复同一路径。官方未支持的平台仍尝试已有兼容运行时或连接器；确实无可行路径时交付已完成部分、具体阻塞与可执行替代方案，不宣称初始化成功。

本次有效方案可记录到用户选定的项目配置或任务临时文件，包含系统、版本、工具路径、来源、动作与复验结果。不写入凭证或安装包，不自动修改全局记忆或Skill；后续读取仍需核对版本与路径。没有联网能力时使用本地help与已安装工具，未知安装步骤标待确认。

## 企微路径

CLI安装包基线为 `@wecom/cli`，命令为 `wecom-cli`。先查当前包元信息中的 engines、bin 与官方说明；依其要求选择 Node/npm，不固定过时版本。已有 npm 且权限合适时可执行 `npm install -g @wecom/cli`；全局目录不可写时采用经当前 npm help 验证的用户目录 prefix，并在本次进程使用其真实路径。不使用sudo强行全局安装。

Windows常见入口为 `.cmd` 或 PowerShell 包装器。配套Python脚本会读取已安装 `@wecom/cli/package.json` 的bin入口，用node参数数组执行，支持常见全局与项目本地npm布局。找不到入口时返回 `runtime_adapter_required`；由助手检查实际npm prefix、包目录与bin，不反复运行失败包装器。初始化器也会返回对应中文说明。不能为传入JSON改用 `shell=True`，也不放宽系统PowerShell执行策略。

CLI版本不低于1.2.1后检查 `auth show --status`。未授权时先查 `auth init --help`；支持时用 `auth init --noninteractive` 显示本次授权链接或二维码，让本人完成授权，随后复查。未知响应先查当前契约，不当成成功或反复初始化。

环境修复不创建业务资源。用户已要求连接验证时，继续 [新建、编辑与回读](onboarding.md)；普通用例整理直接回到原任务。安装成功、账号授权、文档操作和业务验收分层报告。

## 验证边界

本包在macOS执行本地测试。Windows包装器、中文路径和异常恢复使用临时目录与模拟响应测试；Linux/Windows真实安装与授权须在对应机器复验。新增平台也使用同样的“识别、修复、复验”流程，不预填通过。
