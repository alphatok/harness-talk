# 合作机会雷达｜找方向、筛机会、定推进

把“双方似乎可以合作”收敛成有付费方、有业务结果、有责任边界、有证据门禁的机会组合。不要从行业标签直接套方案，也不要把对方默认成最终采购方。

## 必要输入

尽量取得以下信息；缺失项作为待核问题，不得自行补全：

- 目标公司：主体、产品、客户、项目、合作伙伴、收入线索和公开声量；
- 我方能力：能做什么、成熟度、案例、交付边界、部署与安全条件；
- 接触阶段：未接触、初聊、已有线索、招投标、合同或交付中；
- 商业约束：地区、行业、客单价、账期、数据合规、排他或品牌要求；
- 交付目标：速判、标准分析、深度机会设计，及 Markdown、HTML、演示稿等格式。

只有公司名称时，先做公开信息核实。若已有尽调报告，复用其证据台账，优先解决未闭环的身份、客户、合同和产品成熟度问题。事实可能变化或用户要求联网时，应查询当前公开来源。

## 工作模式

- **速判**：识别经营模式、给出最多 3 个机会假设、关键风险和下一次会谈问题。适合首次线索筛选。
- **标准**：形成完整机会组合、优先级、商业结构、推进路线、红线与证据账本。默认模式。
- **深度**：在标准版基础上补充上下游、竞争替代、单位经济性、多角色决策链、投标/验收机制和行业复制路径。

用户没有指定时，根据资料量选择；不能因为资料少而制造确定性。

## 核心工作流

### 1. 建立证据底座

先锁定法律主体、品牌、域名、账号和关键人物，防止同名串线。区分：

- `F`：可核事实；
- `C`：企业、销售或第三方宣称；
- `I`：基于已列证据的推断；
- `U`：未知或待核。

重要结论同时记录来源等级、发布日期/访问日期和反证。搜索无结果只能表述为“在已检索范围内未发现”，不能证明不存在。

### 2. 形成经营模式指纹

分别回答九个问题：谁付钱、为何付钱、公司控制什么稀缺资源、如何获客、谁定义需求、谁交付、谁验收、如何回款、如何复制。

从 [经营模式与路由](references/archetypes-and-routing.md) 选择一个主模式和零至两个副模式，并给出置信度与证据。主模式由**资金流、客户控制权、交付责任**决定，不由宣传文案决定。混合型公司保留各模式权重，不强行单选。

### 3. 还原交易系统

画出或表述四类角色：目标公司、最终使用者、预算/合同主体、实际交付者。进一步闭合六条链：

1. 商机链：线索从哪里来，谁能接触最终客户；
2. 决策链：谁发起、影响、拍板和否决；
3. 合同链：谁与谁签约，是否允许分包；
4. 资金链：预算、付款节点、账期和坏账承担者；
5. 交付链：方案、产品、集成、上线、运维分别由谁负责；
6. 验收链：谁定义结果、谁签字、出现偏差谁整改。

角色或链路不清时，机会只能停留在假设级。

### 4. 系统生成机会池

使用 [机会生成引擎](references/opportunity-engine.md)。至少从以下四个维度组合：

`对方控制的资源 × 我方可验证能力 × 付费方业务事件 × 可签约商业单元`

先发散，再去重。不得仅列我方产品功能；每个机会必须说明客户为何现在付钱、双方各自不可替代之处以及最小成交单元。

### 5. 门禁与排序

按照 [证据、阶段与商业门禁](references/evidence-commercial-gates.md) 将机会标为 `H0–H5`，并检查最终客户/预算方、问题、交付边界、验收责任和付款结构。

可用 `scripts/score_opportunities.py` 对候选机会做一致性排序。分数用于比较，不替代商业判断；硬门禁未通过时，不得因高分而承诺资源。

### 6. 设计合作结构

为高优先级机会比较直接采购、技术分包、联合投标、联合解决方案、嵌入/OEM、托管运营、推荐分佣或生态服务等结构。至少明确：

- 客户和商机归属；
- 售前成本与退出条件；
- SOW、变更、里程碑、验收和付款；
- 数据、知识产权、品牌呈现与案例使用；
- 一方失约、回款延迟或项目失败时的责任；
- 从单项目升级为行业包或长期合作的客观条件。

### 7. 形成验证路线

用“下一次会谈 → 机会资格确认 → 付费验证 → 首单交付 → 复盘复制”的门禁路线。每一阶段写清输入、动作、输出、负责人、截止时间和退出条件。初次合作优先以一个实名机会验证，不以框架协议代替真实交易。

### 8. 输出与自检

标准/深度模式按 [交付标准](references/deliverable-standard.md) 产出；跨工具或跨系统运行时遵循 [可移植执行](references/portability.md)。

结论必须先于过程，且始终分开呈现事实、宣称、推断和未知。若证据不足，给出验证动作和降级合作方式，不用空泛的“建议加强合作”收尾。

## 不可违反的判断原则

- 不把“有关系”当作客户控制权，不把培训学员当作项目客户。
- 不把代码仓库、演示或功能清单当作生产交付证明。
- 不把知名机构同框、入驻园区或口头背书当作投资/隶属关系。
- 不在最终客户、预算、验收责任未明时承诺免费 POC、排他、兜底回款或无限售前。
- 不因模板完整而填补未知信息；证据不足本身就是结论。
- 不照抄固定行业方案。相同能力在买方、渠道、集成商和平台公司中，应映射为不同合同单元和责任边界。
